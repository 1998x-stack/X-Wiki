# X-Wiki PRD v2.0 — Evidence-First Living Knowledge

> 状态：**待实现的产品规格**（不是已上线功能） | 更新：2026-11-03  
> 关联基线：[PRD v1](./PRD.md)、[UX-001 工程验收](./UX-001.md)、[PH/HN 用户研究](./research/PH-HN-2026.md)、[Review Workbench 详细规格](./specs/Knowledge-Review-Workbench.md)、[Product Hunt 发布计划](./launch/Product-Hunt-Playbook.md)

## 1. Executive decision

**产品命题**：X-Wiki 的下一阶段是一个“可追溯的思考变化审阅工具”，而不是又一个记录 + AI 摘要 + 聊天应用。

**价值主张**：新记录来到时，系统优先找到与用户**当前已有认识**最相关的证据，呈现“这是否改变了旧观点？”；用户可以选择保留、修订、标记矛盾或忽略。所有接受的变化可回看、可撤销、可直接导出到其拥有的 Markdown 文件。

**北极星指标（候选）**：每个每周活跃用户在 28 天内完成的**有来源、经本人批准、后来再次被使用的知识修订**次数（Verified Knowledge Reuse）。它同时要求真实用户控制与复用，而非堆积语音量、笔记数量、AI 调用或自动链接数。初期样本不足时先用“首次有证据修订完成率”做代理，不在仪表盘宣称已测得真实留存。

**差异化测试**：
- 对照 A：普通转录 + 摘要；
- 对照 B：自动关联 + Ask Notes；
- 实验 C：有来源、有原文 Diff、有人工批准、带版本记录的知识修订。
只要 C 对独立真实任务不优于 A/B，放弃“Living Knowledge 是核心差异”假设，不能继续靠加功能补救。

## 2. 产品现实与真实交付边界

截至 2026-11-03 可核对的仓库基线：\`iPhone Voice Memos → iCloud/Mac → MLX Whisper 本地转录 → immutable raw → pi+Skill 编译 → wiki/Markdown → Git → GitHub Pages\`；已有 staged-compiler、Wiki Lint、Git 发布清单、恢复日志、Pages HTTP 读回及 \`/demo/\` 合成六步交互。

**尚未交付**：无终端真实文件导入、桌面安装器、用户可审阅的真实 ChangeProposal、来源逐字位置级对齐、决策召回、真实授权隐私页面、多平台移动捕捉。不得让市场文案暗示这些现已存在。

**数据风险**：本地 Whisper ≠ 全链路全本地。pi 可能调用外部 provider。默认展示数据流与是否出站，并经明确同意后调用；没有实现选择隔离前不能标“fully offline AI”。

## 3. ICP 和明确排除的需求

### Primary: Independent thought workers

用户每天或每周口述/速记，持续几周反复修改同一主题；痛点不在生成一页干净摘要，而在找回旧想法、认识自己在哪改变了主张、保留依据。示例：独立写作者、学生研究者、独立开发者长期技术判断、创业者自身决策记录。

### Secondary: Local Markdown/Obsidian owners

已经有自己的目录和工作流，不愿迁移资料。价值是旁路索引、证据审阅和衔接既有 Vault；产品不强迫其使用另一个编辑器。

### Anti-persona / 不优先支持

仅需要会议纪要发给同事的团队；期待自动把每段音频都转成 Todo 的用户；需要跨组织审批/合规会议记录的企业；将知识图谱可视化节点数量视为主要目标的用户。

**关键反例**：HN 明确有用户不愿 AI 自动生成或主动提醒（研究 HN-06/07）。首版必须保留“只读关联、按需搜索、无推送”模式。产品不应把所有 Source 转换成 Claim，也不能把所有 Claim 转任务。

## 4. 用户旅程（真实产品，不是合成演示）

| 阶段 | 用户动作 | 系统输出 | 最容易失去信任的失败 | 必要控制 |
|---|---|---|---|---|
| 1 First-run | 安装并导入一段文件 | 可见进度、源文件落盘确认 | 录音丢失、安装复杂、权限不明 | 不覆盖原文、失败重试/导出 |
| 2 Capture | 文件/语音/现有 Vault | Source ID、时间、hash、转写修订 | AI 改写原文、重复导入 | 原始内容与清理文稿分层 |
| 3 Discover | 打开审阅收件箱 | 最多 1–3 条高质量候选/批次 | 过多弱关联、伪矛盾 | 过滤、理由、无变化状态 |
| 4 Review | 点开某个提案 | old vs proposed、原句、证据强弱 | 找不到来源、裁决过度 | source jump、拒绝/编辑/保留 |
| 5 Approve | 明确点击批准 | 新 Revision、差异与恢复令牌 | 静默覆盖、版本竞态 | 乐观锁、可撤销、审计 |
| 6 Recall | 按主题/决定/大概想法搜索 | 历史主张和精确依据 | AI 编造答复、搜不出同义想法 | FTS 降级、引用、明确无结果 |
| 7 Reuse | 打开旧知识并用于工作 | 哪个观点起作用及其时间轨迹 | 只收藏不用、无实际复用 | 自愿标记“used”, 不用打卡式任务 |

首发完整体验要求**至少两条相隔时间的个人证据**；如果只有一段文件，则只能创建初始知识节点，不应假装检测出“观点演化”。

## 5. 关键功能与 DoD

### P0-A: Import & Capture (AC-01)

- 从 Finder 拖入 \`.m4a/.mp3/.wav/.txt/.md\`（具体支持格式以端到端验收为准）；导入后先原文保存，再派生处理。
- 每个 Source 至少记录 \`source_id\`, \`source_sha256\`, \`captured_at\`, \`imported_at\`, \`origin\`, \`processing_state\`。
- \`processing_state\`: queued → importing → stored → transcribing → indexed/failed_retryable/failed_terminal；与下游修订状态分离。
- 重复导入相同 hash 应产生“已存在”提示而不是重复知识；文件丢失时展示缺失和恢复途径，不能显示虚假成功。
- 允许始终读取/导出未经 AI 改写的原始内容。
- **验收**：中断/磁盘满/转写异常注入后，至少没有已成功确认但不可找回的来源；重试幂等；来源 hash 可验证。

### P0-B: Evidence-linked Review Workbench (AC-02)

- 新来源到达时输出 \`New Node | Enrich | Qualify | Contradict | No Change | Uncertain\` 之一，并说明为什么。
- 提案不必全部进入用户队列；低于阈值的候选可归档为“无需更新”或“不确定”，不自动编造摘要。
- 展示 before/after Diff、时间顺序、依据原句和页内跳转。
- 原文片段缺失、来源不可读、版本过期、无法明确证明时阻止静默批准，并且允许编辑提案。
- 仅用户批准后写入知识资产；拒绝/撤销不可改写原 Source。
- **验收**：对合成+授权真实测试集，硬性禁止错误 source ID、越界引用、没有原文支持的断言直接变成事实。更详细状态见[Workbench Spec](./specs/Knowledge-Review-Workbench.md)。

### P0-C: Trust & Privacy Control Plane (AC-03)

- 模型处理面板明确区分：Whisper local、LLM provider local/external、Git push、Pages public。
- 真实 Source 默认只在本机；若 LLM 外发，需要明确显示目标 provider、会发送哪些文本、处理目的，并让用户授权/取消/失败后重试。
- 应允许“只做本地导入索引、禁止远端 LLM”的降级模式，且不因此丢失素材。
- 共享或网页发布以**逐页面且可读回**的权限为准；发布预览呈现将公开的全文、标题、路径、引用和元数据。
- **验收**：未获明确同意时网络拦截测试无外发；内容包清点无 raw、token、文件系统隐私路径；撤销权限后无新外发。

### P0-D: Migration / Ownership (AC-04)

- 原始 Markdown 文件视为用户可持续拥有的资产；索引缓存/向量索引为可重建派生数据。
- Vault 导入先提供 Scan & Preview（总文件数、跳过、无效、冲突、将新增/修改的文件），后执行受控导入。
- 默认不移动、不覆盖、不删除用户原始目录；可退出后直接用 Obsidian、Git、文本编辑器继续使用。
- **验收**：100–1,000 份多目录测试集无静默丢失、无重复 ID、原始文件字节不被改动；导出-再导入保留证据关联与历史版本。

### P1-A: Decision Recall (AC-05)

用户可问“我什么时候决定不采用方案 A？”而不必记得原句。先以确定性的检索定位 \`Decision/Claim/Revision\`，返回日期、当时支持与反对证据、变化历史；允许与关键词 FTS 比较。不给无证据的总括句。

- 搜索界面默认 FAST：FTS5 + 别名/同义词；召回不足时提供可选语义扩展，不强迫用户等大模型。
- 问答必须引用每个相关主张的 EvidenceSpan；若来源被删除/私有不可读，则降级或明确拒答。
- **验收**：独立标注的 50–100 条决策检索查询上报告 Recall@5/MRR@10，和关键词+FTS5 基线比较；问答来源准确率独立评估。

### P1-B: Calm Rediscovery (AC-06)

默认无主动通知；提供 \`Open when needed\` 知识再发现页。用户可选开启周回顾、项目相关提醒。每条“重新发现”应说明：与什么当前问题相关、为什么现在值得看、原文在哪里、如何永久关闭此类提醒。

- **验收**：15 名用户用 7–14 天评估 relevance（有用/忽略/错误）、干扰、回访；“通知次数多”不是成功指标。

## 6. 首页 IA 和真实工作台

主要导航保持五个、按工作目标而不是技术架构分类：
- **Capture**：拖入/录音/文本，队列及失败恢复；
- **Review**：待审阅的知识变化（默认首页，有价值的少量候选）；
- **Knowledge**：当前被批准的概念/决策/项目；
- **Recall**：按需搜索旧决定和观点演化；
- **Privacy & Settings**：数据位置、模型外发、权限、备份/导出。

避免首页使用原始 graph 作为主视觉。可以用“每周节省的人工整理次数”做验证指标，但没实测不能在产品展示中夸张承诺。首屏提供直观的“本次录入 → 发现关联 → 待审阅的修改”，并明确每个状态是 preview、draft 还是 approved。

## 7. 非功能性要求

| 维度 | 设计目标（待评估） | 拒绝发布的条件 |
|---|---|---|
| 数据完整性 | 任何已确认导入的原始文件可 hash 验证；崩溃恢复无静默丢失 | 存在可重现的上传/导入成功却找不到原文 |
| 可信引用 | 已批准提案全部携带可定位引用；不允许引用越界 | 错误引用直接进入用户公开知识库 |
| 无人工默写任务 | 不自动将任一主张转 Todo | 未经批准产生真实外部任务 |
| 索引反馈 | 本地搜索一般查询目标 p95 < 500ms（需真实 corpus 基线） | 搜索阻塞捕捉输入或长时间假性成功 |
| 端到端本地 | 数据去向明确可解释，外发需许可 | 使用“全本地”文案但实际发送给外部 provider |
| 控制权 | 任何 AI 建议在批准前不影响已发布内容 | 审阅界面可被绕过或发生竞态 |
| 无障碍 | 键盘可完成捕捉/审阅/搜索，读屏状态正确 | 主要流程不可键盘操作 |
| 安装 | 新用户无需命令行完成首个真实导入（V1.0） | 只能完成静态合成演示，却宣称已是完整 AI 产品 |

注意：这些数字是 proposed targets，没有当前真实基准。性能/实用性需在目标设备与真实授权数据上测量。

## 8. 产品决策与优先级

| 排序 | Delivery | 用户价值 | 必要前置 | 本阶段完成的定义 |
|---|---|---|---|---|
| 0 | 研究与现有 UX-001 Demo | 展示价值假设 | 已上线演示 | 用户能理解但不冒充真实 AI |
| 1 | P0-A 容错导入 + P0-C 数据边界 | 让用户安心把内容交给产品 | Mac 权限/来源落盘 | 多故障恢复、外发可拒绝 |
| 2 | P0-B Review Workbench | 首个独特完整价值循环 | Claim/Span/Proposal Schema | 人工批准/可撤销/错误安全 |
| 3 | P0-D Markdown Migration | 尊重已有知识工作流 | ID/历史导入策略 | 可逆导入，迁移无损 |
| 4 | P1-A Decision Recall | 旧知识可真正再利用 | 有授权的长期历史 | 独立 Recall 评估赢过 baseline |
| 5 | P1-B Calm Rediscovery | 长期留存而不打扰 | 用户相关性反馈 | 7–14 天实际用户研究 |
| 6 | Product Hunt launch readiness | 可真实使用的差异体验 | 实际用户路径、隐私审计 | Release Gate 完整通过 |

**不优先**：团队协作、默认 AI 推送、复杂图谱视觉、多端同步、社交广场、超长集成列表。它们会增大工作量，却未必提高验证结果。

## 9. 独立实验：要证明它有用，而不只是能跑

### E1：谁能说清价值？

测试 15–20 位目标用户（至少两组 persona），无需提示地访问 /demo/。记录理解准确率、点击步骤、完成时间、真正认为有价值的细节。建议阈值：≥80% 能准确讲出“来源支撑的、用户可控的知识修订”；完成时间中位 ≤90s。**不是现有结果**。

### E2：修订是否比摘要更好？

对相同的 30–50 组双来源资料，随机分为 A 纯摘要、B 自动连边、C 证据审阅。评委独立标记事实支持、误判、耗时和接受度。要求 C 的可靠性显著好于 A/B，且没有不可解释的“修订成功”。

### E3：导入是否获得信任？

5–10 位真实用户测试首次导入流程与模拟断电/权限错误。成功标准不只是上传速度，还要看是否保留原始内容，出错时用户是否明确知道当前状态和恢复操作。

### E4：真正重复使用了吗？

在明确同意后收集 28 天队列数据：经审阅的知识节点在另一任务中被重新打开、引用或编辑的事件数。单纯记录数、会话数和点赞不能代表有用知识。

## 10. 伦理与发布叙述

- X-Wiki 不把笔记变成义务，不鼓励毫无必要的捕捉行为。
- 用户原文是原文，模型判断是模型判断；不同意见可以长期共存。
- 隐私、安全、用户控制是功能的一部分，而不是“以后再加”。
- GitHub Pages 公共 Wiki 与私有用户 Workspace 严格分离；不得以公开 Wiki 成功来证明私人审阅流程已完成。
- Product Hunt 必须基于**实际可用**的产品及真实演示。现有 /demo/ 是合成模拟，不应宣传为端到端已上线的 AI 产品。
- 不将任何 Product Hunt 评分或 HN 代表性有限的用户意见包装成市场覆盖率。

## 11. 待回答的重大产品问题（研究而非猜测）

1. 用户宁可安装一个完整 Mac 工作台，还是更愿意要 Obsidian 旁路插件？
2. 用户愿意接受多少比例的新记录完全没有后续建议？
3. 来源事实与个人观点矛盾是否应走不同的审阅模式？
4. 语言支持应先中文/英文，还是目标用户已要求其它语言？
5. Privacy-first 是否意味着**严格全设备推理**才能赢得目标群体，而不仅是可选择外发？
6. 付费动力源于“真实节省整理时间”还是“可找回过去的决定”？不应在无付费实验前定价。

**下一项执行任务**：先完成 P0-A 的无命令行真实录入与状态真实性，然后完成 P0-B 的来源审阅工作台与独立证据评测；不是继续增加一个新的“漂亮但虚构”的互动页面。
